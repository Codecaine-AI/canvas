# Multi-agent automated code review

We need a diagram of how our automated code-review pipeline works, beginning when a pull request event reaches the intake service. Intake resolves the diff, changed files, repository review policy, and build status. It rejects draft pull requests and excludes vendored or generated paths before invoking any model work. For an eligible change, the context builder assembles diff hunks, surrounding source, related tests, ownership metadata, and prior review history for the touched files. Its budget forces it to rank the material, truncate lower-value context, and record everything it drops.

The planner partitions the change into review units and dispatches correctness, security, performance, test-coverage, and API-compatibility reviewers concurrently over the shared context. Each reviewer returns findings with a current-file location, severity, rationale, and confidence. Reviewers may call read-only repository search, symbol lookup, and test-history tools within a per-review call budget. A reviewer that exhausts this allowance returns its available findings rather than delaying the run.

The aggregator merges the parallel results, deduplicates overlapping findings, reconciles conflicting severities, and withholds low-confidence findings. It checks the current branch head and drops any finding whose location no longer exists. Before publication, the verifier rechecks every high-severity finding against the actual source. An unverified finding is demoted instead of posted, because false positives on a pull request are the failure the team most wants to avoid.

Surviving findings become inline comments and a summary verdict. Depending on repository policy, the pipeline can request changes, approve, or remain advisory. Author replies and human reviewer disagreements return to the calibration process. A finding resolved as wrong is recorded, and the calibration store adjusts the confidence threshold for that finding class in later reviews.

A head-change monitor cancels an in-flight review when a force-push or new commit arrives, starts a fresh review against the new head, and discards partial work rather than publishing it against the wrong diff. The telemetry service tracks cost, latency, token usage by reviewer, cancellation rate, and the accepted-versus-dismissed rate of published findings. When a repository exceeds its daily review budget, intake degrades subsequent runs to correctness and security review only. The diagram should make clear how failures and feedback affect the review lifecycle.
