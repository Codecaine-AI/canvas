# LLM inference gateway with routing and fallback

We need a diagram of how our platform's inference gateway works: it exposes one endpoint to client applications, which request a capability tier instead of a particular backend. The edge service authenticates the caller, resolves tenant identity and quota, and stamps a request id that follows every attempt. An admission controller enforces per-tenant concurrency and token-rate limits. Excess work waits in a deadline-aware queue; if its deadline passes, the controller rejects it explicitly and tells the caller to retry instead of serving it late.

The router selects a backend within the requested tier from live health, measured latency, queue depth, price, and the tenant's data-residency requirements. Eligible capacity includes hosted provider endpoints spread across independent accounts and a self-hosted pool managed by its own scheduler. Before dispatch, a prompt assembler applies tenant system context and safety policy. A response cache returns exact matches and semantically near-duplicate deterministic results, keyed by prompt, parameters, and policy version.

The gateway streams tokens to the caller as they arrive. Before any token is emitted, failures are classified as timeout, rate-limit rejection, content-policy refusal, backend overload, or malformed response. Retryable failures move to the next backend in the tier's fallback order with a fresh deadline and the same idempotency key; non-retryable failures return immediately. After streaming begins, a backend failure cannot be silently retried elsewhere: the gateway either completes the stream or visibly fails it while preserving what the caller already received.

Circuit breakers open after sustained backend errors or timeouts and drain new traffic toward healthy capacity. They admit a trickle of shadow probes before closing again. Metering records tokens, latency, selected backend, cache outcome, and cost into a billing stream, while redacted prompts and responses enter an audit store. A tenant that reaches its spend ceiling first degrades to the cheapest capable backend and then has new work rejected.

A small sample of structured evaluation traffic is mirrored to a shadow backend, whose result never changes the client response. The diagram should make clear how admission, routing, caching, fallback, streaming, capacity protection, and accounting interact, especially how requests behave under overload and provider failure.
