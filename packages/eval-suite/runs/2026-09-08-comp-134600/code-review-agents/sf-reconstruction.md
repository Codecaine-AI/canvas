# SF blind system reconstruction

## SYSTEM PURPOSE
A budgeted pull-request code-review procedure that resolves and filters intake without model work, builds shared context, dispatches concurrent specialist reviews, merges and verifies findings, publishes inline comments and a repository-policy verdict, cancels and restarts on a changed head, and uses post-publication adjudication and telemetry for calibration.

## COMPONENTS
- 1 · Intake / no model work: Intake stage that resolves the pull-request event and filters the review scope before any model work. [Blue region titled “1 · Intake / no model work” containing “PR event → resolve intake” and “Reject drafts; filter paths.”]
- PR event → resolve intake: Resolve the incoming pull-request event and intake information. [Rounded process labeled “PR event → resolve intake” at the top of the intake region.]
- Reject drafts; filter paths: Reject draft pull requests and filter paths before passing eligible work onward. [Rounded process labeled “Reject drafts; filter paths,” reached by a downward solid arrow from intake resolution.]
- Intake-resolution requirements: Resolve the diff, changed files, review policy, and build status; exclude vendored or generated paths before model work; reduce review scope when the daily budget is exceeded. [Yellow note in intake: “Resolve diff, changed files, review policy and build status. Exclude vendored / generated paths before model work. Daily budget exceeded → correctness + security only.”]
- 2 · Budgeted context: Construct a ranked shared context within a token budget. [Blue region titled “2 · Budgeted context.”]
- Rank & truncate context: Rank candidate context and truncate it to the available budget. [Rounded process labeled “Rank & truncate context,” receiving the main flow labeled “eligible” and emitting a flow labeled “shared context.”]
- Shared context: Provide diff hunks and surrounding source, related tests and ownership, and prior review history; rank within the token budget, truncate lower-value material, and log omissions. [Yellow note: “Shared context • Diff hunks + surrounding source • Related tests + ownership • Prior review history Rank within token budget; truncate lower-value material and log every omission.”]
- 3 · Concurrent review / shared context: Partition the shared context and dispatch concurrent specialist reviews that use the same bounded context. [Teal region titled “3 · Concurrent review / shared context.”]
- Planner: partition & dispatch: Partition review work and dispatch it to the visible specialist reviewers. [Rounded process labeled “Planner: partition & dispatch,” receiving the “shared context” arrow and branching to five review processes.]
- Correctness: Review the dispatched material for correctness findings. [Top specialist process labeled “Correctness,” with an incoming arrow from the planner branch and an outgoing line toward merge.]
- Security: Review the dispatched material for security findings. [Specialist process labeled “Security,” with an incoming arrow from the planner branch and an outgoing line toward merge.]
- Performance: Review the dispatched material for performance findings. [Specialist process labeled “Performance,” with an incoming arrow from the planner branch and an outgoing line toward merge.]
- Test coverage: Review the dispatched material for test-coverage findings. [Specialist process labeled “Test coverage,” with an incoming arrow from the planner branch and an outgoing line toward merge.]
- API compatibility: Review the dispatched material for API-compatibility findings. [Bottom specialist process labeled “API compatibility,” with an incoming arrow from the planner branch and an outgoing line toward merge.]
- Reviewer operating requirements: Constrain each reviewer to read-only search, symbol lookup, and test history; return available findings when its call budget is exhausted; and report current-file location, severity, rationale, and confidence. [Yellow note: “Each reviewer • Read-only search, symbol lookup, test history • Call budget exhausted → return available findings • Return current-file location, severity, rationale, confidence.”]
- 4 · Merge, verify & publish: Merge specialist findings, verify high-severity findings, produce comments and a verdict, and route unverified findings away from publication. [Green region titled “4 · Merge, verify & publish.”]
- Merge & deduplicate findings: Combine the outputs of all specialist reviewers and remove duplicate findings. [Rounded process labeled “Merge & deduplicate findings,” receiving the joined reviewer outputs.]
- Finding reconciliation requirements: Reconcile conflicting severities, withhold low-confidence findings, check findings against the current head, and drop findings whose locations no longer exist. [Yellow note: “Reconcile conflicting severities; withhold low confidence. Check current head; drop findings whose locations no longer exist.”]
- Verify high severity in source: Verify surviving high-severity findings against source before they are eligible for publication. [Rounded process labeled “Verify high severity in source,” reached from merge by an arrow labeled “survivors.”]
- Demote; do not post: Demote a high-severity finding that cannot be verified and prevent it from being posted. [Rounded process labeled “Demote; do not post,” reached by a red downward arrow from verification labeled “unverified.”]
- Inline comments + verdict: Produce inline review comments and the final verdict for eligible verified output. [Rounded process labeled “Inline comments + verdict,” reached from verification by an arrow labeled “eligible.”]
- Repository policy: Limit the verdict to requesting changes, approving, or issuing an advisory. [Yellow note: “Repository policy: Request changes, approve, or advisory.”]
- Lifecycle control · cancellation & budget: Control cancellation and restart behavior when the reviewed head changes, with budget-related intake restrictions. [Red region titled “Lifecycle control · cancellation & budget.”]
- Head change → cancel run: Cancel the current review run when the pull-request head changes. [Rounded process labeled “Head change → cancel run” connected to the red dashed restart route.]
- Force-push / new-commit policy: Discard partial work, prohibit publishing against the old diff, and restart intake on the new head. [Yellow note: “Force-push / new commit: Discard all partial work; never publish against the old diff. Restart intake on the new head.”]
- Calibration & operational telemetry: Collect operational telemetry and use adjudicated wrong findings to calibrate later classification thresholds. [Blue lower region titled “Calibration & operational telemetry.”]
- Telemetry service: Track cost, latency, tokens by reviewer, cancellation rate, and accepted versus dismissed findings; use the daily repository budget to limit later runs. [Yellow note: “Telemetry service Cost, latency, tokens by reviewer; cancellation rate; accepted vs dismissed findings. Daily repository budget → intake limits later runs to correctness + security.”]
- Author replies / disagreements: Receive post-publication author responses or disagreements. [Rounded process labeled “Author replies / disagreements,” reached by a downward arrow from “Inline comments + verdict” labeled “published review.”]
- Record wrong findings; calibrate: Record adjudicated wrong findings and feed calibration back toward finding handling. [Rounded process labeled “Record wrong findings; calibrate,” receiving a left-pointing arrow from author replies labeled “adjudicate” and emitting a dashed blue feedback route.]

- The pull-request head changes because of a force-push or new commit.: Head change → cancel run → Discard all partial work → Never publish against the old diff → Route via “new head: restart” → PR event → resolve intake on the new head → The old run is cancelled and intake restarts against the new head. [Red lifecycle-control region, process “Head change → cancel run,” force-push/new-commit note, and red dashed restart route to intake.]
- A high-severity finding is unverified during “Verify high severity in source.”: Verify high severity in source → Take the red downward route labeled “unverified” → Demote; do not post → The finding is demoted and is not posted. [Red downward arrow labeled “unverified” from verification to “Demote; do not post.”]
- A reviewer exhausts its call budget.: Reviewer call budget is exhausted → Return available findings → The reviewer stops further work and returns whatever findings are available. [Reviewer note states: “Call budget exhausted → return available findings.”]
- The daily repository budget is exceeded.: Daily repository budget is exceeded → Apply intake limits to later runs → Limit those runs to Correctness and Security → Later review runs omit the other visible specialist classes and run correctness plus security only. [Intake note says “Daily budget exceeded → correctness + security only”; telemetry note says “Daily repository budget → intake limits later runs to correctness + security.”]
- A finding has low confidence, conflicts in severity, refers to a location that no longer exists, or does not survive the current-head check.: Merge & deduplicate findings → Reconcile conflicting severities → Withhold low confidence → Check current head → Drop findings whose locations no longer exist → Only surviving findings proceed to high-severity source verification. [Merge note gives all listed checks and removals; the outgoing edge to verification is labeled “survivors.”]

[Bottom-right flow labels “published review,” “adjudicate,” and “later: class thresholds,” plus process “Record wrong findings; calibrate.”]
