# SF blind system reconstruction

## SYSTEM PURPOSE
Canary delivery with automatic rollback: build and verify an immutable revision, promote the same digest through staging, obtain approval, canary it first in a primary region and then independently in a secondary region, automatically freeze or roll back on failed health checks, and maintain control-plane state, audit evidence, and operator notifications.

## COMPONENTS
- 1 · Protected build & supply chain: Contains the protected source, build, scan, gate, and immutable-image production process. [Light-blue bounded section labeled “1 · Protected build & supply chain”.]
- Signed source revision: Provides the signed source revision entering the protected build process. [Blue box labeled “Signed source revision” at the beginning of section 1.]
- Pipeline coordinator: Coordinates the pipeline from the protected source branch into build and test execution. [Blue box labeled “Pipeline coordinator”, connected from the source and toward the install/compile/test box.]
- Install • compile • unit • integration: Installs dependencies, compiles the revision, and runs unit and integration work before scanning. [Gray box labeled “Install • compile • unit • integration”, followed by an arrow labeled “then scan”.]
- SCA + image vulnerability scans: Performs software-composition and image-vulnerability scanning. [Orange box labeled “SCA + image vulnerability scans”.]
- All gates pass?: Decides whether the build and security gates permit publication. [Yellow decision box labeled “All gates pass?”, with a green publication path and a red “no · stop” path.]
- Immutable image + provenance: Represents the immutable deployable image and its provenance after all gates pass. [Green box labeled “Immutable image + provenance” reached from “All gates pass?” by a green line whose visible text includes “publish”.]
- Build/supply-chain failure path: Stops the revision, notifies the owner, and fails the gate; security and signature gates cannot be bypassed. [Red box stating “**Failure path** Stop revision; notify owner with failed gate. Security and signature gates cannot be bypassed.”]
- 2 · Staging promotion: Promotes the same immutable digest into staging, validates signature and database compatibility, deploys services, runs staging tests, and records approval or stops promotion. [Purple bounded section labeled “2 · Staging promotion”.]

- DB compati...: Performs a database-compatibility-related check before migration. [Yellow box visibly labeled “DB compati...” after the “verify signat...” connector.]
- Backward-compatible migration: Applies or represents a backward-compatible database migration before service deployment. [Purple box labeled “Backward-compatible migration” between the database compatibility box and “Deploy services”.]
- Deploy services: Deploys services in staging and feeds the validation loop. [Purple box labeled “Deploy services”, with a gray line looping toward the staging tests and labeled “validate”.]
- Smoke + contract tests: Runs smoke and contract tests against the staging deployment. [Gray box labeled “Smoke + contract tests”.]
- Staging healthy?: Evaluates staging test results and branches to approval or failed-staging handling. [Yellow decision box labeled “Staging healthy?”, receiving a connector labeled “results”.]

- 3A · Primary-region canary & automatic rollback: Runs a primary-region canary, evaluates telemetry and thresholds over consecutive windows, ramps healthy traffic, pauses when telemetry is unavailable, and automatically rolls back unhealthy deployment. ## FAILURE PATHS
- “All gates pass?” evaluates to “no”.: SCA + image vulnerability scans → All gates pass? → no · stop → Failure path → Stop the revision, notify the owner with the failed gate, and do not publish the immutable image. [Red return path labeled “no · stop” ends at the red note: “Stop revision; notify owner with failed gate. Security and signature gates cannot be bypassed.”]
- The staging health decision fails after smoke and contract test results.: Smoke + contract tests → results → Staging healthy? → Failed staging check → Stop promotion and preserve staging logs and artifacts. [Red arrow from “Staging healthy?” to the red “**Failed staging check**” box containing the stated outcome.]
- Primary telemetry is unavailable.: Telemetry available? → PAUSE for operator review → Operator authority → Pause for operator review; after telemetry recovers, the operator may resume or order rollback. [Downward orange path from the telemetry decision to the pause and dashed blue path to the operator-authority note.]
- Primary canary thresholds are unhealthy.: Thresholds healthy? → Freeze rollout → Rollback primary to last known-good image → Compensation declared... → Run compensating action → Freeze the primary rollout, restore the last known-good image, and follow the depicted compensating-action path when applicable. [Red path connects the threshold decision to freeze and rollback; lower connectors link rollback with the compensation-related and compensating-action boxes.]
- “Secondary healthy?” follows the path labeled “failure”, and the shared-business decision is “no”.: Secondary healthy? → failure → Freeze secondary rollout → Shared business... → no → Rollback secondary region only → Only the secondary region is rolled back. [Red failure route and “no” branch terminate at “Rollback secondary region only”; the failure-scope note says a secondary failure is isolated to that region.]

[The “yes” branch terminates at “Rollback both regions to last known-good image”; the note explicitly says only a shared business-metric breach triggers rollback in both regions.]

## CONSTRAINTS & BOUNDARIES
- The delivery uses the same immutable image/digest through promotion rather than rebuilding it for staging or regional rollout. [Labels “promote same digest”, “Same immutable image”, “Immutable image + provenance”, “same immutable revision”, and “primary complete · same revision”.]
- Security and signature gates cannot be bypassed. [Build failure note explicitly states “Security and signature gates cannot be bypassed.”]
- Operator authority never permits bypassing failed security gates or image-signature verification. [Operator-authority note explicitly says “Never bypass failed security gates or image-signature verification.”]
- Staging promotion requires signature verification, database compatibility work, a backward-compatible migration, deployment validation, healthy staging results, and approval. [Ordered staging boxes and labels show “verify signat...”, “DB compati...”, “Backward-compatible migration”, “Deploy services”, “validate”, “Smoke + contract tests”, “Staging healthy?”, and “yes · require approval”.]
- Primary and secondary canaries begin at 5% traffic and healthy ramps proceed through 25%, 50%, and 100%. [Both regional sections contain “5% traffic”; green ramp boxes show “25% → 50% → 100%”.]
- Primary health evaluation occurs over consecutive observation windows. [Primary section contains the box “Consecutive observation windows”.]
- Secondary health evaluation uses independent observation windows. [Secondary section contains the box “Independent observation windows”.]
- Every evaluation window considers error rate, latency, saturation, and business success. [The “**Evaluate every window**” note lists those four metrics.]
- If telemetry is unavailable, the rollout pauses for operator review rather than automatically proceeding. [Alternate path from “Telemetry available?” enters “PAUSE for operator review”.]
- The secondary canary begins only after the primary is complete, and it uses the same immutable revision. [Primary-complete box says “Begin the secondary canary with the same immutable revision”, and its green output is labeled “primary complete · same revision”.]
- A normal secondary failure is isolated to the secondary region; only a shared business-metric breach rolls back both regions. [Blue “**Failure scope**” note states this boundary explicitly.]
- Rollback targets are the last known-good image. [Primary rollback and both-regions rollback boxes explicitly say “last known-good image”.]
- Audit evidence is append-only and includes rollout state and approvals, metric decisions, traffic changes, and rollback actions. [Control-plane evidence box explicitly says “**Append-only evidence**” and lists those four categories.]
- Operators are notified at every promotion, pause, failure, and recovery. [Blue control-plane note explicitly states “Notify at every promotion, pause, failure, and recovery.”]
