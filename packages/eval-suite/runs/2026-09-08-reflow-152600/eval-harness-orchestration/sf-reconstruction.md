# SF blind system reconstruction

## SYSTEM PURPOSE
An offline evaluation harness that runs pinned, versioned scenarios under bounded execution, grades completed scenarios immediately and concurrently, preserves evidence and verdicts, and compares scorecards only against a compatible chosen baseline to produce defensible comparisons.

## COMPONENTS
- Offline evaluation harness: Encloses the end-to-end system for pinned runs and defensible comparisons. [Top-level board label: “Offline evaluation harness • pinned runs → defensible comparisons”.]
- 1 · Pinned input & bounded execution: Contains pinned-suite execution, bounded workers, the isolated system under test, step-outcome handling, and run recording. [Left cyan region titled “1 · Pinned input & bounded execution”.]
- Pinned suite: Provides the pinned suite from which a pinned run starts. [Gear/config icon labeled “Pinned suite”, connected downward by “start pinned run”.]
- Frozen-scenario and fingerprint policy: Requires changed scenario wording to create a new version and defines the run fingerprint inputs. [Yellow note: “Frozen scenarios: new wording → new version, never edit in place. Fingerprint: tested revision, config, prompt versions, rubric versions.”]
- Scheduler: Coordinates the pinned run and fans work out to the bounded worker pool. [Orchestrator icon labeled “Scheduler”; incoming route “start pinned run” and outgoing route “fan out” to the worker pool.]
- Bounded worker pool / Ordered scenario steps: Executes ordered scenario steps using a bounded pool and accepts continued or retried work. [Predefined-process shape labeled “Bounded worker pool / Ordered scenario steps”; routes include “fan out”, “execute steps”, “more steps • continue”, and “log infra fault • retry”.]
- Isolated SUT / Never production: Runs scenario steps against an isolated system-under-test environment that is explicitly not production. [Server icon labeled “Isolated SUT / Never production”, below the “execute steps” route.]
- Step outcome?: Branches after an observed result into infrastructure retry handling or success/product-failure recording. [Decision diamond labeled “Step outcome?”; incoming “observed result”, red route “log infra fault • retry”, and downward route “success / product failure”.]
- Record behavior / success / Full transcript + artifact: Records behavior or success and retains the full transcript and artifact for the completed execution path. [Process labeled “Record behavior / success / Full transcript + artifact”; it receives the “success / product failure” route and connects to continuation, grading, and archival routes.]
- 2 · Immediate, concurrent grading: Contains concurrent criteria grading, artifact-only grading, evidence validation, retry control, invalid-verdict handling, and valid-verdict routing. [Pink region titled “2 · Immediate, concurrent grading”.]
- Global grading limit: Coordinates grading under a global limit and dispatches grading work. [Orchestrator icon labeled “Global grading limit”, reached by “scenario complete → grade now”; outgoing paths are labeled “parallel criteria” and “artifact only”.]
- Independent criteria graders: Grade criteria independently and return a verdict with evidence. [Judge icon labeled “Independent criteria graders”; incoming route “parallel criteria” and outgoing route “verdict + evidence”.]
- Artifact-only grader: Grades only the artifact, without the original request, and returns a verdict with evidence. [Judge icon labeled “Artifact-only grader / No original request”; incoming route “artifact only” and outgoing route “verdict + evidence”.]
- Evidence present?: Checks whether grader output has evidence and separates valid verdicts from missing or invalid results. [Decision diamond labeled “Evidence present?”; receives two “verdict + evidence” routes, emits “yes • valid verdicts”, and emits “no • invalid”.]
- Already retried?: Determines whether an invalid grader result should be retried or flagged after a prior retry. [Decision diamond labeled “Already retried?”; reached from “no • invalid”, with outcomes “no • retry grader” and “yes • flag”.]
- Flag invalid verdict / Exclude from scorecard: Marks an invalid verdict and excludes it from the scorecard when the retry has already been used. [Process labeled “Flag invalid verdict / Exclude from scorecard”, reached by the “yes • flag” route.]
- 3 · Compatible comparison: Builds scorecards from valid verdicts, verifies baseline compatibility, compares compatible scores, and manages promotion to the future baseline. [Right region titled “3 · Compatible comparison”.]
- Assembler / Merge valid verdicts → scorecard: Merges valid verdicts into a scorecard. [Process labeled “Assembler / Merge valid verdicts → scorecard”, reached by “yes • valid verdicts” and followed by “run scorecard”.]
- Chosen baseline: Stores the selected baseline and supplies its fingerprint and scores for compatibility checking. [Blue store icon labeled “Chosen baseline”; route to the comparison decision is labeled “baseline fingerprint + scores”.]
- Same fingerprint?: Checks whether the run scorecard and chosen baseline have the same fingerprint. [Decision diamond labeled “Same fingerprint?”; it receives “run scorecard” and “baseline fingerprint + scores”, then branches to “no” or “yes • compatible”.]
- No comparison / Incompatible runs: Stops comparison for runs whose fingerprints are incompatible. [Process labeled “No comparison / Incompatible runs”, reached by the “no” branch from “Same fingerprint?”.]
- Compare scores / Narrate |Δ| ≥ threshold: Compares compatible scores and narrates absolute score differences meeting or exceeding a threshold. [Process labeled “Compare scores / Narrate |Δ| ≥ threshold”, reached by “yes • compatible”.]
- Promote run / Future compatible baseline: Promotes a run to become a future compatible baseline. [Process labeled “Promote run / Future compatible baseline”; incoming dashed route “on promotion” and outgoing route “set future baseline” to the chosen-baseline store.]
- Run archive / Re-examine scores: Stores run transcripts, artifacts, fault types, and retained verdicts for later score re-examination. [Blue store labeled “Run archive / Re-examine scores”; incoming routes are labeled “transcripts + artifacts + fault types” and “retain every verdict”.]

## FAILURE PATHS
- A step outcome is an infrastructure fault.: Step outcome? → log infra fault • retry → Bounded worker pool / Ordered scenario steps → The infrastructure fault is logged and the work is retried through the bounded worker pool. [Red loop labeled “log infra fault • retry” returns to the worker pool.]
- A step outcome is a product failure.: Step outcome? → success / product failure → Record behavior / success / Full transcript + artifact → The product failure follows the recording path, including the full transcript and artifact; the diagram does not show a product-failure retry. [The same downward edge is explicitly labeled “success / product failure” and enters the recording process, while only the infrastructure-fault branch is labeled as a retry.]
- Evidence is absent or the grader result is invalid, and the grader has not already been retried.: Evidence present? → no • invalid → Already retried? → no • retry grader → Global grading limit → The grader is retried. [The red invalid route reaches “Already retried?” and the “no • retry grader” branch loops back to grading.]
- Evidence is absent or the grader result is invalid after a retry has already occurred.: Evidence present? → no • invalid → Already retried? → yes • flag → Flag invalid verdict / Exclude from scorecard → The verdict is flagged invalid and excluded from the scorecard. [The “yes • flag” branch terminates at the process whose text explicitly says “Exclude from scorecard”.]
- The run scorecard and chosen baseline do not have the same fingerprint.: Same fingerprint? → no → No comparison / Incompatible runs → No comparison is performed because the runs are incompatible. [The red “no” branch terminates at “No comparison / Incompatible runs”.]

## CONSTRAINTS & BOUNDARIES
- Runs use pinned input and bounded execution. [Region title “1 · Pinned input & bounded execution” and process label “Bounded worker pool”.]
- Scenario wording is immutable in place; new wording requires a new version. [Note states: “Frozen scenarios: new wording → new version, never edit in place.”]
- A fingerprint includes the tested revision, configuration, prompt versions, and rubric versions. [Note states: “Fingerprint: tested revision, config, prompt versions, rubric versions.”]
- Scenario steps are ordered. [Worker-pool process explicitly says “Ordered scenario steps”.]
- The system under test is isolated and never production. [Server label reads “Isolated SUT / Never production”.]
- Grading begins immediately when a scenario completes. [Region title says “Immediate, concurrent grading” and the crossover route says “scenario complete → grade now”.]
- Grading concurrency is bounded by a global grading limit. [Orchestrator is labeled “Global grading limit” and dispatches parallel criteria and artifact-only work.]
- Criteria grading is parallel and performed by independent criteria graders. [Route label “parallel criteria” enters the judge component “Independent criteria graders”.]
- The artifact-only grader receives no original request. [Judge component is labeled “Artifact-only grader / No original request”.]
- Grader outputs are expected to contain both a verdict and evidence. [Both grader output routes are labeled “verdict + evidence” and converge on “Evidence present?”.]
- Only valid verdicts are merged into the scorecard. [The “yes • valid verdicts” route enters “Assembler / Merge valid verdicts → scorecard”; invalid repeated verdicts are explicitly excluded.]
- Every verdict is retained in the run archive, including verdicts outside the valid-scorecard path. [Archive route is labeled “retain every verdict”.]
- Comparison is allowed only when the run and baseline fingerprints match. [Decision “Same fingerprint?” sends “yes • compatible” to comparison and “no” to “No comparison / Incompatible runs”.]
- Comparison narration is limited to absolute deltas meeting or exceeding a threshold. [Comparison process says “Narrate |Δ| ≥ threshold”.]
- A baseline changes only on the explicitly shown promotion path. [Dashed route “on promotion” reaches “Promote run / Future compatible baseline”, followed by “set future baseline” into the chosen-baseline store.]
- Execution records preserved in the run archive include transcripts, artifacts, and fault types. [Archive input route is labeled “transcripts + artifacts + fault types”.]
