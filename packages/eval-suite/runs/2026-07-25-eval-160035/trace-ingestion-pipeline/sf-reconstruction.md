# SF blind system reconstruction

## SYSTEM PURPOSE
Distributed trace ingestion: collect spans from instrumented services, survive host/outage conditions, authenticate and govern regional ingest, durably partition and log spans, assemble traces, tail-sample them fairly, control storage/cardinality, extract unbiased metrics for query and alerting, and apply self-observation-driven saturation policy.

## COMPONENTS
- 1 · Host instrumentation & outage survival: Collect spans on hosts, batch and compress them, and buffer them on bounded disk during an outage for later draining. [Blue subsystem labeled “1 · Host instrumentation & outage survival” contains “Instrumented services,” “Batch + compress agent,” and “Bounded disk buffer,” with labels “spans,” “buffer on outage,” and “drain after recovery.”]
- Instrumented services: Originate spans for ingestion. [Server icons labeled “Instrumented services” send a rightward arrow labeled “spans” to the agent.]
- Batch + compress agent: Batch and compress incoming spans before sending them to the regional ingest gate; interact with the outage buffer. [Blue box labeled “Batch + compress agent” receives “spans,” sends a blue arrow to “Authenticate,” and has dashed blue buffer/drain paths.]
- Bounded disk buffer: Temporarily store agent data during an outage, within a bounded disk capacity. [Gray box labeled “Bounded disk buffer” is reached by a dashed blue path labeled “buffer on outage” and returns through a dashed path labeled “drain after recovery.”]
- 2 · Regional ingest gate: Authenticate incoming data, enforce tenant rate limits, and validate schema before durable logging. [Orange subsystem labeled “2 · Regional ingest gate” contains “Authenticate,” “Tenant rate limit,” and “Validate schema,” joined by directed arrows.]
- Authenticate: Authenticate data arriving from the host batch/compression agent. [Orange box labeled “Authenticate” receives the blue arrow from “Batch + compress agent” and points to “Tenant rate limit.”]
- Tenant rate limit: Apply a per-tenant ingest rate limit before schema validation. [Orange box labeled “Tenant rate limit” is downstream of “Authenticate” and has a directed path down to “Validate schema.”]
- Validate schema: Validate the schema of rate-limited ingest data before it enters the durable trace log. [Orange box labeled “Validate schema” receives the path from “Tenant rate limit” and sends a gray path toward “Partition by trace ID.”]
- 3 · Durable trace log: Partition spans by trace ID and write them to a durable span log while preserving trace locality. [Teal subsystem labeled “3 · Durable trace log” contains “Partition by trace ID,” “Durable span log,” and a trace-locality note.]
- Partition by trace ID: Assign spans to partitions according to trace ID. [Teal box labeled “Partition by trace ID” receives the validated ingest path and points to “Durable span log.”]
- Durable span log: Durably record partitioned spans. [Teal box labeled “Durable span log” is directly downstream of “Partition by trace ID.”]
- 4 · Trace assembly: Wait for trace completion, restore the parent-child tree, classify completion state, and emit assembled traces. [Purple subsystem labeled “4 · Trace assembly” contains “Completion window,” “Restore parent-child tree,” and “Root seen or window expired,” with directed paths among them and onward to sampling.]
- Completion window: Hold spans during a completion window before trace reconstruction. [Purple box labeled “Completion window” receives the purple path labeled “out of order spans” and points to “Restore parent-child tree.”]
- Restore parent-child tree: Reconstruct the parent-child structure of a trace. [Purple box labeled “Restore parent-child tree” is downstream of “Completion window.”]
- Root seen or window expired: Represent the condition under which trace assembly proceeds: the root has been seen or the completion window has expired. [Purple box labeled “Root seen or window expired” is reached by a downward arrow labeled “complete / incomplete” and sends a purple path labeled “assembled trace” to the sampler.]
- 5 · Tail sampling & fairness: Tail-sample assembled traces, favor specified trace classes, and protect tenant fairness through retention floors. [Amber subsystem labeled “5 · Tail sampling & fairness” contains “Tail-based sampler,” “Errors · slow · small share,” and a tenant-fairness note.]
- Tail-based sampler: Make tail-based sampling decisions on assembled traces. [Amber box labeled “Tail-based sampler” receives the purple “assembled trace” path and points to “Errors · slow · small share.”]
- Errors · slow · small share: Identify or retain the displayed sampling categories: errors, slow traces, and a small share. [Green-outlined box labeled “Errors · slow · small share” is downstream of the tail-based sampler and sends the green path labeled “retained traces.”]
- Tenant fairness policy: Use retention floors to protect quiet tenants from noisy neighbors. [Amber note states “Tenant fairness” and “Retention floors protect quiet tenants from noisy neighbors.”]
- 6 · Storage & cardinality control: Apply a cardinality guard, store retained traces in hot storage, and age data into cold trace storage. [Green subsystem labeled “6 · Storage & cardinality control” contains “Cardinality guard,” “Hot trace storage,” and “Cold trace storage.”]
- Cardinality guard: Control cardinality before retained traces enter hot storage. [Green box labeled “Cardinality guard” receives the “retained traces” path and points to “Hot trace storage.”]
- Hot trace storage: Store guarded traces in the hot storage tier. [Green box labeled “Hot trace storage” is downstream of “Cardinality guard” and has a downward path labeled “age out.”]
- Cold trace storage: Receive traces that age out of hot trace storage. [Gray box labeled “Cold trace storage” receives the directed path labeled “age out” from “Hot trace storage.”]
- 7 · Unbiased metrics, query & alerting: Extract metrics from every trace and support rate/error/latency views, search, dependencies, series, queries, and alerting. [Pink subsystem labeled “7 · Unbiased metrics, query & alerting” receives a path labeled “every trace” and contains the metrics/query pipeline and a query-and-alert note.]
- Metrics extractor: Extract metrics from every trace independently of the retained-trace storage path. [Pink box labeled “Metrics extractor” receives the downward pink arrow associated with the label “every trace” and points to “Rate · errors · latency.”]
- Rate · errors · latency: Produce or represent rate, error, and latency metrics. [Pink box labeled “Rate · errors · latency” is downstream of “Metrics extractor” and points to “Search · dependencies · series.”]
- Search · dependencies · series: Provide search, dependency, and series capabilities from the metrics pipeline. [Pink box labeled “Search · dependencies · series” is downstream of “Rate · errors · latency.”]
- Query & alert experience: Provide trace search, service dependencies, derived series, and alerts linked to exemplar traces. [Pink note states “Query & alert experience” and “Trace search · service dependencies · derived series · alerts linked to exemplar traces.”]
- 8 · Self-observation & saturation policy: Observe lag, occupancy, rates, and drops; detect persistent saturation; and apply a prioritized load-shedding policy. [Red subsystem labeled “8 · Self-observation & saturation policy” contains a directed sequence from “Lag · occupancy · rates · drops” to “Persistent saturation” to the load-shedding priority note.]
- Lag · occupancy · rates · drops: Monitor the displayed operational signals: lag, occupancy, rates, and drops. [Red box labeled “Lag · occupancy · rates · drops” begins the self-observation sequence.]
- Persistent saturation: Represent detection or continuation of persistent saturation based on observed operational signals. [Red box labeled “Persistent saturation” receives a red arrow from “Lag · occupancy · rates · drops” and points to the load-shedding policy.]
- Load-shedding priority: Order shedding so ordinary retention yields first while error traces and metrics extraction are preserved. [Red note states “Load-shedding priority” followed by “1. Ordinary retention yields first 2. Preserve error traces 3. Preserve metrics extraction.”]
